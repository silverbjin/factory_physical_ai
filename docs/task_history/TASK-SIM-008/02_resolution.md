# Resolution — TASK-SIM-008

## Root Cause

The original `SIM_NORMAL_E2E_BLOCKED` had two independent causes: restricted
sandbox networking prevented DDS interface discovery and UDP sockets, and the
Gazebo-only path eagerly imported the optional MuJoCo backend. The previously
applied lazy imports and fail-closed optional dependency handling remain in
place.

The later `SIM_NORMAL_E2E_READY` was not authoritative because
`GazeboSystemWorld.state` was both the commanded state and the verification
observation. It did not observe the task object in Gazebo. Once that defect was
removed, a second live-run failure exposed an ordering error: the object was
moved onto the destination before Nav2 drove the robot to that same point.
The live collision monitor intervened and the controller reported
`Failed to make progress`.

## Fix

- `scripts/run_simulation_normal_system_e2e.py` launches the task-owned SIM-008
  world, applies the transition through Gazebo's `/set_pose` service, and reads
  the object back independently through `/generate_world_sdf` plus `/stats`.
- `src/simulation_runtime/normal_system_e2e.py` requires the full authoritative
  observation record, validates world/entity/source/shape/current-execution
  freshness, and fails closed for unavailable, malformed, stale, or mismatched
  observations.
- Mission ordering is source navigation and verification, destination
  navigation, Gazebo placement, then final authoritative verification. This
  avoids placing the observed object in the Nav2 goal before arrival.
- The SIM-008 world and scenario declare the observed Gazebo entity, while the
  shared navigation launcher accepts an explicit world path without changing
  its SIM-004 default.
- Focused regressions prove process-local state cannot satisfy acceptance,
  missing or stale authoritative observations fail closed, and matching live-
  record-shaped observations pass.
